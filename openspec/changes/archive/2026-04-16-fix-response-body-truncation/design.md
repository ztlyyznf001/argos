## Context

当前 `KurilHttpInfo.toJson()` 会对 `request.parameters.join()` 和 `response.result` 统一调用 `truncateBody()`，超过 100KB 就只保留前 100KB 并附加 `"[TRUNCATED]"`。这个策略最初用于限制 MMKV 存储膨胀，但它直接破坏了抓包工具最重要的调试信息之一: 响应体全文。

现有链路里，UI 层和复制能力都只消费 `KurilPacketRecord.responseBody`，因此一旦存储时被截断，后续没有机会恢复原始内容。另一方面，`http-capture-pipeline` 已经对非文本响应只记录元数据，所以真正需要讨论的是文本响应的存储策略，而不是所有响应类型都无限放开。

## Goals / Non-Goals

**Goals:**
- 让文本响应体在 `KurilPacketRecord` 中按实际捕获结果完整保存
- 保持非文本响应不写入 `responseBody`，避免把图片、文件或任意二进制塞进文本存储
- 把变更范围控制在存储与展示链路，不引入新的用户配置和额外依赖

**Non-Goals:**
- 不修改 `maxPacketRecords` 的淘汰策略
- 不新增按体积上限、内容类型或 host 的可配置截断规则
- 不改变请求体当前的截断行为，除非实现时发现必须统一重构公共函数

## Decisions

### 决策 1：响应体与请求体分离存储策略

不再复用统一的 `truncateBody()` 处理请求体和响应体。请求体继续沿用现有保护策略，响应体改为单独分支处理。

原因是两者的调试价值和体积特征不同：请求体通常较小，截断影响相对可控；响应体尤其是 JSON 列表、详情数据、GraphQL 返回值，超过 100KB 并不罕见，而且一旦截断就直接影响定位问题。

备选方案：统一取消请求体和响应体的截断。这个方案实现更简单，但会明显扩大单条记录体积，且不符合当前用户提出的问题边界，因此不选。

### 决策 2：只对文本响应完整保存

继续依赖上游 `http-capture-pipeline` 的内容类型判断，只有文本响应才写入 `responseBody`。对于图片、音视频、压缩包或其他二进制响应，仍保持 `responseBody = ''`，只记录 `responseCode`、`responseHeaders` 和 `responseSize`。

备选方案：把所有响应都以 base64 形式完整落盘。这个方案会显著增加存储量，也会让详情页和复制行为变得混乱，因此不选。

### 决策 3：本次不引入配置项

先把默认行为修正为“文本响应完整保存”，不增加类似 `maxResponseBodyBytes` 的配置。

原因是当前问题来自默认行为本身错误地牺牲了调试可用性，而不是用户缺少调参入口。先消除错误默认值，再根据真实使用情况决定是否需要后续引入上限配置。

## Risks / Trade-offs

- [文本响应较大时单条记录体积增加] → 依然受 `maxPacketRecords` 总条数约束；若后续出现明显存储压力，再单独提变更引入响应体上限配置
- [旧数据中仍可能存在 `"[TRUNCATED]"`] → 这是历史记录格式，新的实现只保证后续写入完整；不做存量 MMKV 数据迁移
- [请求体与响应体使用不同规则后，公共函数结构会变化] → 在实现时把 body 处理逻辑显式拆分，并补充测试覆盖两类路径，避免行为回退
